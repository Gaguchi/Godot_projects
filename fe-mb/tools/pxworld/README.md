# pxworld

The code that draws Embermarch's pixel world, plus the Filigree UI mockups that sit on it. It builds every board on the design canvas (https://claude.ai/artifact/79397vba2Fwp6Wti5a6DLj, private) and the bare world art under them.

Nothing here is generated by an image model or drawn in a paint program. Every pixel is placed by Python (numpy and Pillow) following written rules. The characters are the exception: they are the game's own sprites from the ComfyUI pipeline, and this code only places them, at exactly 1:1.

## Setup

- Python 3.11, then `pip install -r requirements.txt`.
- For previews only: Node, plus Playwright from `game/` (`cd game && npm install`, then `npx playwright install chromium` once).

## Rebuild

From `tools/pxworld/`:

```
python rebuild.py                    # every board, about 7 minutes
python rebuild.py PxCamp F64Title    # only the generators that write these boards
python rebuild.py --preview          # also screenshot each board to out/preview/
```

What it writes:

| Folder | What |
|---|---|
| `out/boards/` | the 22 canvas boards (`<Board>.dc.html`) and the canvas layout (`canvas.json`) |
| `out/world/` | the world each screen is drawn on, at 1×, with no UI: `map`, `map_no_company`, `combat_field`, `town_inn`, `town_shop`, `town_tavern`, `camp`, `title`, `prologue`, `dungeon`, `win`, `lost` |
| `out/preview/` | PNG screenshots of the boards, with the art swapped in from `assets/` |

All of it is ignored by git and comes back with one rebuild.

Each generator runs in its own process. That matters, because the scene folders forked their own copies of a few helpers (`people.py`, `ground.py`, `fire.py` and others), so two generators in one process would pick up the wrong one.

The build is deterministic: the same code writes the same bytes on every run. To check a change, rebuild before and after and compare `out/boards/`. Seeds are fixed numbers. Never seed from `hash()` of a string, because Python salts it per process. The dungeon did that until 2026-10-24.

`assets/up/` holds copies, not originals:

| Image | Source |
|---|---|
| `board_*.png` | `game/public/sprites/units/board/` |

If the game's sprites change, copy them in again.

The build reads three files from the game: `game/src/content/data/classes.json`, `items.json` and `dialogue/prologue.json`.

## How the art is made

1. **Palette.** There are 16 ramps, dark to light, in `src/pxworld/pal.py`: the UI's 7 plus grass, leaf, pine, water, dirt, stone, wheat, roof and skin. The canvas holds palette indices, not colours, so nothing can drift off the palette.
2. **One function per thing.** For example, `build.cottage(14, 'ew', roof='thatch')` draws a house in the map's three-quarter view. Bridges, tents, wagons, trees and wells each have their own function.
3. **Light from the upper left.** A shadow moves a pixel down its own ramp. A cast shadow is the ground one step darker, with a hard edge. There are no gradients and no blur.
4. **Selout outlines.** Each part is outlined in the darkest step of its own ramp, not black, and lighter on edges that face the light.
5. **Texture drawn by rule.** Roof courses, mortar, wood grain and grass clumps are drawn on purpose, never per-pixel noise. Curves use hand-picked steps.
6. **Scenes.** Things that stand up become sprites with a foot point, y-sorted onto painted ground. One scale per scene.
7. **QA.** Render, crop the busy parts at 3–5× with nearest-neighbour, compare against the bar in `docs/PXWORLD.md`, fix it, then do the same again.

`docs/PXWORLD.md` is the bar the world was drawn to, and it is current. `docs/SCREENS.md` holds the screen rules, which still apply, but it predates the pixel world, so ignore its painted-world line. `docs/BRIEF.md` was the brief for the five competing directions in round 2. It is kept for the board format, the asset table, the forbidden looks and the game facts.

## Using the art in Godot

The repo root is the Godot project. The empty `.gdignore` here keeps Godot from importing this folder.

To use the PNGs from `out/world/`:
- Project Settings → Rendering → Textures → Default Texture Filter: Nearest.
- Display → Window → Stretch: mode `viewport`, scale mode `integer`, base size 1280×720.
- Rendering → 2D: snap 2D transforms to pixel.

What the code does not do yet:
- **Separate sprites.** Buildings, trees and props are composed into one picture. Each is already a separate sprite with a foot point before it is stamped, so writing them out as PNG plus offset, for y-sorted Sprite2D nodes, is a small change.
- **Tiles.** The ground is painted across the whole canvas, not as tiles. Battle maps that vary would need the terrain rewritten to output a TileSet with edge transitions. That is the biggest job.
- **UI as 9-slices.** The UI frames come out as SVG for the canvas. Godot wants them as PNG 9-slices for StyleBoxTexture.
